# Use AI to assist analyst review

Use AI to rank eligible candidates and explain its suggestions. Keep every eligible alternative accessible to the analyst, and continue review using evidence generated by the reconciliation engine if AI is unavailable. The engine enforces eligibility and confirmation rules, and the analyst decides which proposal to accept.

The AI response is a structured, ordered list of candidate IDs with an integer match score from 0 to 100 and short explanations in `pt-BR` and `en` for each candidate. Generate both explanations in the same request and persist them with one shared score and rank per candidate. Accept the result only when the list contains exactly the supplied candidate IDs, each once, with a valid score and both explanations for every entry. Show the score as an AI assessment alongside the stored explanation for the selected locale. Changing the interface language selects the corresponding explanation from the same evaluation. If the response is invalid, use the engine's ordering and evidence.

## Ranking during reprocessing

For each internal transaction, request a ranking when no valid evaluation covers all current pending proposals. Evaluate all pending alternatives together, including when a new proposal enters the group or a previous run used the engine fallback. If proposals only leave the group, reuse the most recent applicable ranking and preserve the relative order of the remaining proposals. Store each successful group evaluation separately from the original proposal evidence and preserve the evidence associated with earlier decisions.

## Provider integration

Keep the local demo usable without AI credentials by using the engine's ordering and evidence. With credentials configured, send ranking requests to a real provider through an application-owned candidate ranking interface. Share request preparation, result validation, and fallback behavior across providers. Each adapter handles authentication and translates requests and responses for its provider's API. One configured provider serves the MVP, and additional adapters can use the same interface.

Send temporary candidate IDs and the transaction descriptions needed for comparison. Replace detected personally identifiable information and account or card details with placeholders before sending descriptions. Keep the mapping local to the request and use it to resolve returned identifiers and placeholders against the original candidates.

Use the OpenAI Responses API with Structured Outputs for the initial provider adapter. Configure the model at startup and apply the shared candidate validation and fallback to its response.

## Usage limits

Bound outbound AI requests and their size in the application. If a usage limit blocks a ranking request, keep all eligible proposals available with the engine's ordering and evidence, and record the reason for the fallback.

If the complete review group exceeds the request size limit, use the engine's ordering for the whole group and keep every proposal visible. A ranking request compares a complete group in one evaluation.

Default to at most five AI calls per reconciliation job and 50 per day across the application. Both limits are configurable. Atomically reserve each call in PostgreSQL before contacting the provider so both limits apply across workers and process restarts.

Make one outbound attempt per ranking evaluation, with a request timeout. If the attempt fails, use the engine's ordering and evidence immediately. Failed attempts count toward both call limits.
